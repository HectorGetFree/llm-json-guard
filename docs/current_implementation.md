# llm-json-guard 当前实现说明

## 1. 项目定位

`llm-json-guard` 用于将不稳定的 LLM 文本输出转换为可信的 JSON 和目标 Go 类型。

它主要解决以下问题：

- 模型使用 Markdown 代码块包裹 JSON；
- JSON 混在自然语言中；
- 全角结构标点、单引号、裸键、尾随逗号或括号缺失；
- JSON 虽然语法合法，但不符合目标类型、Schema 或业务规则；
- 本地处理失败后，需要一次可选的 LLM 修复。

项目目前定位为一个可配置的 JSON 防护库，不是模型网关，也不负责模型选择、负载均衡或业务数据补全。

## 2. 当前处理链路

```text
LLM 原始输出
  → 输入与 Schema 大小检查
  → 编译 JSON Schema
  → 原始输出严格解码、Schema 校验和业务校验
  → 标准化字符串外的全角结构标点
  → 从 Markdown 和普通文本中提取 JSON 候选
  → 候选严格解码、Schema 校验和业务校验
  → 对语法非法候选执行安全本地修复
  → 修复结果重新执行统一校验
  → 必要时最多调用一次 LLM 修复
  → LLM 结果重新执行统一校验
  → 返回可信结果或结构化错误
```

链路按照成本和风险从低到高执行。无论结果来自原始输出、候选提取、本地修复还是 LLM 修复，都必须经过同一个 `decodeAndValidate` 信任边界。

## 3. 现有能力

### 3.1 JSON 提取

- 支持原始纯 JSON；
- 支持 Markdown JSON 代码块；
- 支持从自然语言中提取对象和数组；
- 支持嵌套对象和数组候选；
- 支持不完整的最外层候选，为本地修复提供输入；
- 支持候选去重、数量限制和大小限制。

### 3.2 严格解码和校验

- 支持对象、数组和其他 Go 目标类型；
- 拒绝未知结构体字段；
- 拒绝一个候选中存在多个连续 JSON 值；
- 使用 JSON Schema 校验必填字段、类型、范围、数组和额外字段等结构规则；
- 使用可选 `Validator[T]` 补充跨字段或外部状态相关的业务规则；
- 同一份 Schema 同时用于本地校验和 LLM 修复提示。

外部 JSON Schema 引用默认禁止，避免解析 Schema 时产生隐式文件读取或网络访问。

### 3.3 本地修复

安全本地修复默认启用，当前可以处理部分常见格式问题，例如：

- 裸键和单引号；
- 尾随逗号；
- 缺失闭合括号；
- 注释和部分非标准 JSON 表达。

默认安全模式会拒绝已知的有损行为，例如：

- 缺少值时补 `null`；
- 删除 `...`；
- 合并拼接值；
- 自动改变根 JSON 类型。

调用方可以显式使用 `PermissiveLocalJSONRepair` 接受第三方修复库的完整能力，也可以通过 `DisableLocalRepair` 完全关闭本地修复。

### 3.4 LLM 兜底

- LLM 修复只有调用方显式传入 `LLMRepairer` 后才启用；
- 项目提供一个可选的 OpenAI-compatible 默认实现；
- 外部项目可以注入公司内部模型服务或其他供应商实现；
- 修复请求包含原始输出、同一份 Schema 和本地失败原因；
- 支持对象和数组根类型；
- 最多调用一次，失败后不会形成修复循环；
- 默认不允许 LLM 修复合法 JSON 的语义错误；
- LLM 返回结果仍必须通过本地严格解码、Schema 和 Validator。

## 4. 成功路径与错误

成功路径包括：

```text
direct         原始输出直接成功
extracted      候选提取后成功
local_repair   本地修复后成功
llm_repair     LLM 修复后成功
```

失败通过 `ParseError` 返回稳定的 `ErrorCode` 和 `ParseStage`，当前可以区分输入错误、Schema 错误、候选错误、校验错误、有损修复拒绝和 LLM 修复失败等情况。

## 5. 运行时观测

项目当前提供了一个最小化 `ParseObserver`：每次公开 `Parse` 完成后，可以生成一条 `ParseObservation`。

当前记录的信息包括：

- 是否成功、最终路径、错误码和失败阶段；
- Guard 自身总耗时；
- 输入和 Schema 字节数；
- 候选数量和候选限制状态；
- 本地修复尝试次数；
- LLM 调用次数。

默认不记录原始输出、Schema、候选、最终 JSON 或错误详情。未传入 Observer 时不会创建内部 Recorder，也不会启用观测计时和计数。

> 当前观测能力只是第一版简单 Hook，并不是完整的可观测体系。项目尚未提供阶段级耗时、日志实现、Prometheus、OpenTelemetry、持久化、异步队列、模型 Token、成本统计或审计后台。这些能力应由实际接入需求和生产数据决定是否继续建设。

## 6. 离线评测

项目当前提供一套简单的离线 JSONL 评测：

```bash
go run ./cmd/guard-eval -iterations 100
```

它使用带标准答案的人工样本统计：

- 总体准确率；
- 直接成功和恢复成功数量；
- 恢复成功率与恢复增益；
- 误接收、误拒绝和错误值；
- 成功路径与错误码分布；
- 本地链路的 Mean、P50 和 P95 延迟。

当前评测集会保留已知失败样本，例如多个合法 JSON 的歧义输入，用于量化后续改进，而不是追求表面上的 100% 通过率。

> 当前评测也只是工程基线，不是完整评测体系。样本主要由人工构造，不能代表真实模型和业务流量；默认评测不调用在线 LLM，也没有覆盖模型成本、编造数据率、不同供应商差异和人工意图标注。后续需要持续加入脱敏生产样本，才能用于判断项目在真实场景中的价值。

## 7. 当前已知边界

- 多个候选都通过校验时，当前返回第一个候选，可能无法识别模型最终意图；
- 修复库能力较强，安全模式只能拒绝已经识别出的有损行为，不能证明所有修复都绝对无损；
- Schema、Go 类型和 Validator 需要调用方合理划分职责；
- Schema 当前在每次 `Parse` 中编译，高频场景尚未提供预编译和缓存；
- OpenAI-compatible 默认修复器不能代表所有供应商协议；
- 完整恢复链路并不适合所有调用，高风险业务可能更适合严格校验后快速失败。

## 8. 当前阶段判断

项目已经具备可运行的 JSON 提取、修复、校验和单次 LLM 兜底链路，也具备最基础的观测和离线评测入口。

下一阶段应优先通过真实接入数据验证直接成功率、恢复增益、误接收率、延迟和 LLM 成本，而不是继续无边界地增加修复规则、Hook 或供应商适配。
